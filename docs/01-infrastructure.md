# Этап 1. Подготовка облачной инфраструктуры

Цель из ТЗ: создать сервисный аккаунт Terraform, подготовить S3 backend, описать VPC с подсетями в разных зонах и проверить повторяемость `destroy` → `apply`.

Этот раздел фиксирует последовательность первого этапа. В текущей конфигурации уже добавлены ресурсы Kubernetes второго этапа: для воспроизведения всего проекта читай также [этап 2](02-kubernetes.md). Bootstrap с правами Kubernetes при создании с нуля содержит восемь ресурсов вместо первоначальных четырёх. Основной `destroy` теперь включает кластер.

Все команды ниже выполняются в PowerShell из `C:\Users\khamu\Diplom_YC`. Значения в угловых скобках заменяет владелец. Секреты не нужно присылать помощнику.

## 1. Подготовить аккаунт и локальные файлы

1. В консоли Yandex Cloud проверь активный платёжный аккаунт и наличие средств/гранта.
2. Создай отдельный каталог для диплома или выбери уже созданный. Скопируй его `folder_id` и `cloud_id`.
3. Для первоначального bootstrap используй свою учётную запись с правами создания сервисного аккаунта, назначения ролей в этом каталоге и создания/настройки бакета. Эти права не выдаются аккаунту Terraform.
4. Настрой Yandex Cloud CLI у себя. Клиент подготовлен локально в `.tools/yc/`; вход выполни самостоятельно в своём PowerShell:

   ```powershell
   & .\.tools\yc\yc.exe --config .tools/yc/config.yaml init
   ```

   Используй личную учётную запись с нужными правами для первоначальной подготовки. Команда интерактивная; данные входа вводи только в своём терминале. Конфигурация CLI находится в `.tools/yc/config.yaml`, которая вместе со всей `.tools/` исключена из Git. В другом checkout клиент нужно установить отдельно по [официальной инструкции](https://yandex.cloud/ru/docs/cli/quickstart).

Terraform 1.14.0 уже скачан в `.tools/terraform/` для локальной проверки, контрольная сумма проверена по официальному SHA256SUMS. В новом окне PowerShell добавь его в PATH текущего окна:

```powershell
$env:Path = "$(Join-Path (Get-Location) '.tools\terraform');$env:Path"
terraform version
```

При переносе репозитория на другую машину установи Terraform 1.14.x отдельно: `.tools/` не публикуется.

Локальные копии шаблонов уже созданы, если файлов с такими именами раньше не было:

| Локальный файл | Что заполнить |
| --- | --- |
| `infrastructure/bootstrap/terraform.tfvars` | cloud_id, folder_id, префикс и уникальное имя бакета |
| `infrastructure/terraform/terraform.tfvars` | те же cloud_id, folder_id и префикс; оставить три подсети |
| `infrastructure/secrets.local.ps1` | сначала только YC_TOKEN; два типа ключей аккаунта появятся после bootstrap |
| `infrastructure/terraform/backend.hcl` | имя бакета после его создания |

В новом checkout эти файлы создаются копированием одноимённых `.example` шаблонов. Для `secrets.local.ps1` шаблон называется `secrets.example.ps1`.

После входа получить IAM-токен для bootstrap можно в своём терминале:

```powershell
& .\.tools\yc\yc.exe --config .tools/yc/config.yaml iam create-token
```

Самостоятельно вставь результат в `YC_TOKEN` локального файла секретов. Токен имеет ограниченный срок действия: при ошибке истечения срока получи новый.

Первый запуск делается с токеном владельца для создания или настройки аккаунта, назначения прав и подготовки бакета. Это однократная подготовка; далее основная конфигурация работает от сервисного аккаунта.

### Если сервисный аккаунт уже есть

**Решение для текущего проекта:** создать отдельный аккаунт диплома; существующий `service-acc` и его права не менять. Параметр `existing_terraform_service_account_id` должен оставаться `null` или отсутствовать. Дальнейший текст раздела — справка для альтернативного сценария.

Сначала проверяем его назначение, роли и каталог. Не нужно создавать ещё один аккаунт только потому, что он указан в первоначальном шаблоне.

Для использования существующего аккаунта добавь в локальный `bootstrap/terraform.tfvars` строку, заменив значение настоящим ID:

```hcl
existing_terraform_service_account_id = "ВСТАВЬ_ID_СУЩЕСТВУЮЩЕГО_АККАУНТА"
```

При заполненном ID Terraform не создаёт аккаунт `diplom-terraform`: назначает выбранному аккаунту роль для сети и выводит его ID. Сам существующий аккаунт не включается в управление жизненным циклом Terraform, поэтому Terraform не будет его удалять. JSON авторизованного ключа основной конфигурации должен принадлежать именно этому аккаунту.

Конфигурация добавляет нужные роли, но не удаляет ранее выданные права. Если у аккаунта есть широкие роли или он используется другими проектами, сначала отдельно обсуждаем его пригодность для диплома. Для инфраструктуры и backend используется один выбранный аккаунт; доступ к состоянию предоставляется только на бакет диплома.

Если ID не задан (`null`), сохраняется возможность создания аккаунта с нуля — для воспроизводимости диплома. Не переключай этот параметр после первого применения bootstrap без разбора плана: изменение способа управления уже созданным аккаунтом может запланировать его удаление.

## 2. Создать сервисный аккаунт и бакет через Terraform

После заполнения параметров bootstrap и YC_TOKEN:

```powershell
& .\infrastructure\scripts\Import-Secrets.ps1 -Mode Bootstrap
terraform -chdir=infrastructure/bootstrap init
terraform -chdir=infrastructure/bootstrap fmt -check
terraform -chdir=infrastructure/bootstrap validate
terraform -chdir=infrastructure/bootstrap plan
terraform -chdir=infrastructure/bootstrap apply
```

Проверь план перед вводом `yes`: при создании с нуля ожидаются один сервисный аккаунт, роль VPC для него, один бакет и назначение роли для доступа к этому бакету — четыре ресурса. При использовании уже существующего аккаунта создаются три ресурса. ВМ, кластер и балансировщики на этом этапе не создаются.

Bootstrap создаёт:

| Ресурс | Назначение и права |
| --- | --- |
| `diplom-terraform` или указанный существующий аккаунт | Основной Terraform и S3 backend; `vpc.admin` в каталоге диплома и `storage.editor` только на бакет состояния |
| Бакет с выбранным именем | Закрытый доступ, версионирование, лимит 1 ГиБ, защита от удаления конфигурацией |

При другом `project_name` меняются префиксы имён. На следующих этапах добавим только права, необходимые новым ресурсам. Роли владельца облака, `admin` и универсальная `editor` аккаунту Terraform не назначаются.

Из вывода `apply` сохрани ID аккаунта и имя бакета — это идентификаторы, а не ключи. Выходы `terraform_service_account_id` и `state_service_account_id` содержат один и тот же ID. `bootstrap/terraform.tfstate` хранится локально: сделай приватную резервную копию. Не удаляй этот state и не добавляй его в Git.

## 3. Самостоятельно создать и сохранить ключи

В этом проекте Terraform не генерирует закрытые ключи: владелец создаёт их сам.

1. Для выбранного аккаунта Terraform используй существующий **авторизованный ключ** или создай новый, если такого ключа нет. Сохрани JSON в `infrastructure/secrets/terraform-sa-key.json`. Команда создания нового ключа:

   ```powershell
   & .\.tools\yc\yc.exe --config .tools/yc/config.yaml iam key create --service-account-id <ID_АККАУНТА_TERRAFORM> --output infrastructure/secrets/terraform-sa-key.json
   ```

2. Для того же `diplom-terraform` создай **статический ключ доступа** через консоль: IAM → сервисный аккаунт → создать новый ключ → статический ключ доступа. Сохрани обе части самостоятельно: секретная часть показывается при создании.
3. В `infrastructure/secrets.local.ps1` укажи полный путь к JSON в `YC_SERVICE_ACCOUNT_KEY_FILE`, идентификатор статического ключа в `AWS_ACCESS_KEY_ID`, секретную часть в `AWS_SECRET_ACCESS_KEY`.
4. В `infrastructure/terraform/backend.hcl` укажи фактическое имя созданного бакета. Секреты в этот файл не добавляются.

Авторизованный JSON-ключ используется провайдером Yandex Cloud для создания ресурсов. Статический S3-ключ используется backend для чтения и записи состояния. Эти типы ключей не взаимозаменяемы.

## 4. Создать VPC и подсети с удалённым state

```powershell
& .\infrastructure\scripts\Import-Secrets.ps1 -Mode Infrastructure
terraform -chdir=infrastructure/terraform init '-backend-config=backend.hcl'
terraform -chdir=infrastructure/terraform fmt -check
terraform -chdir=infrastructure/terraform validate
terraform -chdir=infrastructure/terraform plan
terraform -chdir=infrastructure/terraform apply
terraform -chdir=infrastructure/terraform output
terraform -chdir=infrastructure/terraform plan
```

Ожидаемый первый план: одна VPC и три подсети. После применения следующий plan должен сообщить `No changes`.

В бакете должен появиться объект `diploma/infrastructure.tfstate`. Во время изменения Terraform создаёт рядом временный объект блокировки `.tflock`; после успешного завершения он удаляется. Версионирование сохраняет предыдущие версии state. Не запускай изменения из нескольких окон одновременно.

Текущие подсети: `10.10.0.0/24`, `10.20.0.0/24`, `10.30.0.0/24` в `ru-central1-a`, `ru-central1-b`, `ru-central1-d`. Если одна зона недоступна для твоего каталога, замени её на доступную до применения. Для регионального кластера на следующем этапе нужны три зоны; они не должны совпадать. Подсети не должны пересекаться между собой и с будущими диапазонами подов и сервисов.

## 5. Проверить destroy и повторный apply

Этот пункт выполняется, пока в основной конфигурации только сеть. После добавления Kubernetes `destroy` уже удалит кластер и его рабочие узлы.

```powershell
terraform -chdir=infrastructure/terraform plan -destroy
terraform -chdir=infrastructure/terraform destroy
terraform -chdir=infrastructure/terraform apply
terraform -chdir=infrastructure/terraform plan
```

Перед подтверждением удаления проверь: только VPC и три подсети диплома. Бакет и сервисные аккаунты находятся в другом модуле и остаются на месте. После повторного создания ID сети и подсетей изменятся — это ожидаемо. Повторное применение использует те же ключи и backend, ручное пересоздание ресурсов в консоли не требуется.

Сохрани для диплома выводы или снимки `apply`, `destroy`, повторного `apply`, финального `plan` и наличия state в бакете. Перед публикацией убедись, что на них нет ключей и токенов. Не публикуй содержимое state, ключей и локальных секретов.

Этап завершён после выполнения [чек-листа](01-checklist.md). Следующий этап — создание регионального Managed Kubernetes и проверка `kubectl get pods --all-namespaces`.

## Ограничения и расходы

На первом этапе нет платных вычислительных ресурсов: создаются сеть, подсети, аккаунты и бакет. Хранение объектов и запросы к Object Storage оплачиваются по тарифам провайдера. Дальше отдельно учитываем стоимость регионального мастера, трёх прерываемых рабочих узлов, дисков, публичных IP и балансировщиков.

В инструкции экономии из задания приведены старые примеры цен и маленьких дисков. Они не заменяют актуальные ограничения Managed Kubernetes: параметры рабочих узлов определим на следующем этапе. Прерываемость worker nodes обязательна по ТЗ.

`prevent_destroy` защищает бакет от обычного удаления Terraform. Для полного закрытия проекта после защиты потребуется отдельное осознанное удаление сохранённых состояний и bootstrap; для проверки повторяемости на этапе 1 этого делать не нужно.
