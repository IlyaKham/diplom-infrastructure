# Этап 2. Yandex Managed Service for Kubernetes

Цель по ТЗ: региональный мастер, рабочие узлы в трёх подсетях, доступ к кластеру через `~/.kube/config`, успешный `kubectl get pods --all-namespaces`.

## Архитектура

- Один кластер `diplom-k8s`, канал обновлений `STABLE`, Kubernetes `1.35`. Версия проверена через API Yandex Cloud 17 ноября 2026 года.
- Три `master_location` в подсетях `ru-central1-a`, `ru-central1-d`, `ru-central1-e`. По схеме провайдера такой мастер является региональным. Пустая подсеть b этапа 1 заменяется подсетью e из-за недоступных квот рабочих ВМ в b.
- Три группы `diplom-workers-<зона>`, каждая фиксированного размера 1. Это явно обеспечивает по одному рабочему узлу в каждой подсети.
- Каждый узел: `standard-v3`, 2 vCPU с долей 20%, 4 ГиБ RAM, прерываемый, диск 64 ГиБ, containerd. В a/d — HDD, в e — SSD по одобренным квотам. Автоматическое восстановление включено.
- Существующая сеть, аккаунт и бакет сохраняются. Дополнительные облачные аккаунты не создаются.
- `10.96.0.0/16` для подов и `10.112.0.0/16` для сервисов не пересекаются с сетевыми подсетями этапа 1.

4 ГиБ памяти выбраны с учётом будущего Prometheus/Grafana. Диск 64 ГиБ — минимальный размер загрузочного диска группы Managed Kubernetes по документации провайдера. Цены старых маленьких ВМ из инструкции курса нельзя переносить на эту конфигурацию.

## Права одного аккаунта

В `bootstrap/kubernetes-iam.tf` добавлены:

| Роль | Область | Назначение |
| --- | --- | --- |
| `k8s.editor` | Каталог диплома | Terraform создаёт и обновляет кластер и группы узлов |
| `k8s.clusters.agent` | Каталог диплома | Сервис Kubernetes управляет узлами, дисками и балансировщиками |
| `k8s.cluster-api.cluster-admin` | Каталог диплома | Установка компонентов кластера, включая оператор мониторинга |
| `iam.serviceAccounts.user` | Только аккаунт `diplom-terraform` | Назначение этого же аккаунта кластеру и узлам |

Ранее выданный `vpc.admin` обеспечивает сетевые операции, включая публичные адреса. `storage.editor` остаётся ограниченным бакетом состояния. Универсальные облачные роли `admin` и `editor` не назначаются.

Роли назначаются владельцем через bootstrap до применения основной конфигурации. Они не удаляются при `destroy` основного модуля. Для управления инфраструктурой, работы master/node service accounts и доступа администратора используется один выбранный облачный аккаунт, как указал владелец.

## Сеть и доступ

Группы безопасности описаны в `terraform/kubernetes-security.tf`:

1. `diplom-k8s-internal`: связь мастера и рабочих узлов, проверки Network Load Balancer, исходящие подключения к DNS/NTP/API/registry.
2. `diplom-k8s-api`: TCP 443 и 6443 только из `api_allowed_cidrs`. В локальную конфигурацию внесены два проверенных внешних адреса администратора с маской `/32`: VPN и обычное соединение. Доступ для всех IP не включён.
3. `diplom-k8s-workers`: трафик подов и сервисов, NodePort 30000–32767 для последующих публичных LoadBalancer-сервисов. Правило SSH не создаётся.

Узлы получают публичные IPv4 для исходящего доступа; отдельный NAT Gateway не требуется. Публичный endpoint мастера проверяется с TLS и аутентификацией IAM.

При смене внешнего IP нужно обновить `api_allowed_cidrs` в локальном `terraform.tfvars` и применить Terraform. На этапе GitHub Actions отдельно настроим доступ системы деплоя к API.

Во время проверки с SotaVPN первоначальное соединение с API обрывалось на TLS. После добавления второго собственного IP подключение заработало при включённом VPN. Настройки VPN, системные маршруты и проверка сертификата не менялись; дополнительные локальные прокси не использовались.

## Воспроизведение

Все команды запускаются из корня проекта. Секреты остаются в локальном `secrets.local.ps1` и JSON-ключе.

1. Выполнить bootstrap с личной авторизацией владельца, чтобы назначить новые роли. План второго этапа должен добавлять только четыре назначения прав.
2. В основной конфигурации указать `service_account_id` из bootstrap output и `api_allowed_cidrs`.
3. Импортировать локальные секреты и проверить план:

   ```powershell
   .\infrastructure\scripts\Import-Secrets.ps1 -Mode Infrastructure
   .\.tools\terraform\terraform.exe '-chdir=infrastructure/terraform' init '-backend-config=backend.hcl'
   .\.tools\terraform\terraform.exe '-chdir=infrastructure/terraform' validate
   .\.tools\terraform\terraform.exe '-chdir=infrastructure/terraform' plan
   .\.tools\terraform\terraform.exe '-chdir=infrastructure/terraform' apply
   ```

   Для перехода с этапа 1 ожидаются восемь добавлений и одно удаление: новая подсеть e, три группы безопасности, один кластер, три группы узлов; удаляется только пустая подсеть b. Сеть и подсети a/d не пересоздаются. При создании проекта с нуля создаются сеть и подсети, затем семь ресурсов Kubernetes.

4. Настроить доступ:

   ```powershell
   .\infrastructure\scripts\Connect-Kubernetes.ps1
   .\.tools\kubectl\kubectl.exe get nodes -o wide
   .\.tools\kubectl\kubectl.exe get pods --all-namespaces
   ```

Скрипт сохраняет конфигурацию в `C:\Users\khamu\.kube\config`, сохраняя другие контексты, если они есть. Авторизация динамическая через CLI и существующий JSON-ключ; постоянный IAM-токен в kubeconfig не записывается. Текущий контекст называется `diplom`.

Совместимый kubectl 1.35.10 находится в `.tools/kubectl/`; его контрольная сумма проверена по официальному источнику. Если системный kubectl имеет другую минорную версию, используй подготовленный клиент или добавь эту папку в PATH текущего терминала.

Создание регионального мастера и узлов может занять несколько десятков минут. После добавления Kubernetes обычный `destroy` основного модуля удаляет и кластер: цикл пересоздания сети этапа 1 повторять для снимков не нужно.

## Что фиксировать для отчёта

- В консоли: `diplom-k8s`, статус Running/Healthy, региональное размещение мастера.
- Три группы узлов в разных зонах, размер каждой 1, прерываемость ВМ.
- `kubectl get nodes -o wide`: три Ready-узла.
- `kubectl get pods --all-namespaces`: работающие системные поды.
- Итоговый `terraform plan`: `No changes`.

Не показывай содержимое JSON-ключа, профиля CLI или `secrets.local.ps1`. Для снимка подключения достаточно имени контекста и результатов команд.

## Расходы

На этом этапе оплачиваются региональный мастер, рабочие ВМ, 128 ГиБ HDD и 64 ГиБ SSD суммарно, публичные IP и возможный исходящий трафик. Прерываемость и доля CPU уменьшают стоимость рабочих узлов, но не стоимость регионального мастера. Параметры нагрузки зафиксированы в Terraform, чтобы расходы были воспроизводимыми.
